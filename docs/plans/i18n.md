# Plan: translating the RediWM UI

Status: decided. Phase 0 (survey) done 2026-10-08, results below. Next step is
Phase 1.

Scope: this is the groundwork only. It stops hardcoding English so that a
language can be added later by dropping in one `po/<lang>.po` file, with no
code change. No real translation ships as part of it; the `qps`
pseudo-locale is what proves the machinery works.

## Where we are

Every user-facing string is an English literal at its call site
(`"Cancel"`, `"Forget Device"`, `"Delete {s}?"` through `std.fmt.allocPrint`).
There is no gettext, string table or catalog. A rough grep finds ~1,300
capitalised literals under `src/`: `control_center` 609, `files` 361, top-level
`src/*.zig` 531 (power menu, taskbar, notifications, dialogs), `network` 104,
`start_menu` 68, `images` 65, `ui` 56, `desktop` 55, `screenshot` 47,
`editor` 43, `pdf` 38, `polkit` 34. A large share of that is not UI text
(IPC error names, D-Bus members, widget ids, log lines), so the real count is
an output of Phase 0, not an input.

What already exists and the plan builds on:

* `[region] language` is an installed glibc locale (`en_NZ.utf8`).
  `child_env.applyRegion` writes it into `LANG`, `LC_MESSAGES` and `LC_CTYPE`
  of every app the compositor launches, so GTK/Qt apps already follow it.
* `[region] formats` drives the clock (`Taskbar.zig` keeps a private
  `locale_t`) and the `LC_TIME`/`LC_NUMERIC`/... categories for children.
* `start_menu/applications.zig` parses `Name[de]=` locale keys in `.desktop`
  files.
* Text goes through FreeType + HarfBuzz (`ui/text.zig`) with fontconfig
  fallback for missing glyphs, so CJK, accents and emoji draw. The Editor uses
  Pango and has `ime.zig`.
* Tests find widgets by `name` (`ui.find(name, panel=...)`), not by label, so
  most of the suite is insulated from wording. Six files still reference
  English labels (`app_activation`, `keyboard_shortcuts`, `notifications`,
  `bluetooth`, `control_center`, `power`); they run in English and stay valid.

What is missing: any lookup, any catalog, plural handling, and a layout that
tolerates strings of other lengths.

## Goals and non-goals

Goals:

* One lookup API used by the compositor, the standalone apps (Files, Images,
  PDF, Editor, share picker), the lock screen, polkit dialog and greeter.
* English stays the source of truth and the zero-cost default.
* No new runtime library: catalogs are compiled in.
* No per-frame cost: no allocation, no string hashing, no wakeups, no
  growth in idle CPU (`AGENTS.md` "Idle makes no wakeups").
* A pseudo-locale that makes clipped or fixed-width layouts visible without
  knowing any language.

Non-goals (separate plans if wanted):

* **Right-to-left languages.** `ui/text.zig` runs HarfBuzz per run with
  `hb_buffer_guess_segment_properties` but has no bidi reordering (no
  FriBidi) and widgets do not mirror. Arabic/Hebrew/Persian need both.
  Translated Arabic strings would render in the wrong visual order.
* **Input methods in the shell's own text fields.** Only the Editor has IME
  support. A Japanese UI whose control-center fields cannot take Japanese
  input is half-done. Confirmed in Phase 0: the shell has no IME.
* Translating IPC, logs, config keys, `rediwm-msg`, or text produced by other
  programs (D-Bus error messages from NetworkManager/bluez/logind, notification
  bodies, tray menu labels). Those stay as received.

## Design

### The `i18n` module

A leaf named module with no dependencies, importable from `ui`, `config`,
the compositor and every executable, like `ui`/`dbus`/`config` (`AGENTS.md`
"Build and platform").

```zig
i18n.tr("Cancel")                       // msgid is the English text
i18n.trc("menu", "Open")                // context, for same word / different sense
i18n.trn("{n} item", "{n} items", n)    // plural
i18n.fmt(buf, i18n.tr("Delete {name}?"), .{ .name = user })
```

* **English text is the msgid.** Conversion is mechanical (`"Cancel"` →
  `tr("Cancel")`), readable at the call site, and an untranslated string
  falls back to itself. `trc` disambiguates the few collisions.
* **`tr` is allocation-free and hash-free at runtime.** The msgid is a
  comptime literal, so its hash is computed at compile time; the runtime step
  is one probe into the active catalog's open-addressed table plus one `memcmp`
  to confirm. Catalogs are static data in rodata. English is the identity
  with no table at all.
* **Formatting needs a runtime formatter.** `std.fmt` takes a comptime format
  string, and a translated one is only known at runtime. `i18n.fmt` therefore
  substitutes named placeholders (`{name}`, `{n}`) from a struct of strings
  and integers, so translators can reorder arguments. Every existing
  `allocPrint("Delete {s}?", ...)` that carries wording converts to this.
* **Plurals** use CLDR rules, one function per rule family (English/German,
  French, Russian/Polish, Japanese/Chinese: one form, ...). Phase 1 ships the
  rule table; adding a language that needs a new family is a one-function
  change plus a test.
* **Language resolution.** The compositor takes `[region] language` and falls
  back to its own `LC_ALL`/`LC_MESSAGES`/`LANG`. Standalone apps and the
  share picker read the POSIX environment, which `applyRegion` already sets
  when the compositor launches them. Tag `en_NZ.utf8` resolves through
  `en_NZ` → `en` → English. A language with no catalog leaves RediWM's own
  UI in English while apps still get the locale.
* **Pseudo-locale** `qps` (expanded ~40%, accented, bracketed:
  `[Çàñçéł !!!]`) is an ordinary generated catalog selected through the normal
  config key, not an environment hook, so it respects "No test hooks in
  production". It is unlisted in the language picker.

### Catalogs and tooling

* Source: `po/rediwm.pot` (extracted) and `po/<lang>.po`. Standard PO files
  mean contributors can use Poedit, Weblate or any editor, and the format
  carries context and plural forms.
* Extraction and compilation are `build.zig` steps built from one small Zig
  tool (`tools/i18n.zig`), no gettext toolchain needed on the build machine:
  * `zig build i18n-extract` regenerates the `.pot` from `tr`/`trc`/`trn`
    call sites.
  * The normal build compiles each `.po` into a generated Zig file with the
    hash table, embedded in the binaries that use it.
  * `zig build i18n-check` fails on a `tr` literal missing from the `.pot`,
    a stale entry, a placeholder set that differs between msgid and
    translation, or a wrong plural-form count.
* Catalogs are per product, not per executable, so the compositor,
  `rediwm-files` and the rest share one table layout; each binary embeds only
  what it uses if size matters (measure in Phase 1).

### Keeping untranslated strings from creeping back

The risk after the conversion is someone adding `.label = "Foo"`. Two layers:

* `zig build i18n-lint` flags a bare string literal passed to a known UI sink
  (`.label`, `.placeholder`, `text(...)`, `button.paint` labels, dialog
  titles, Cairo `drawText`). A `// i18n: raw` comment marks intentional
  exceptions.
* The lint is opt-in per directory and the list grows with each phase, so it
  never reports the not-yet-converted code.

Widget `name` ids, which tests use, are never translated.

### Switching language

* **Compositor UI:** treated like a theme or scale change. Config reload
  invalidates cached text and rebuilds the panels (taskbar, start menu,
  control center, power menu). No polling; it rides the existing reload path.
* **Running app clients:** pick up the new language on next launch. Nothing
  broadcasts; the Control Center says so next to the setting. (Revisit only
  if users ask.)

### Layout

Translated text is typically 20–40% longer (German, Russian, Finnish) and CJK
text is taller. Likely trouble spots:

* 129 `fixed = N` sizes in `control_center`, `start_menu` and `ui`.
* Hand-placed Cairo layouts with literal offsets and widths, for example the
  Editor close dialog (`.w = 115`, `.w = 120`) and parts of Files.
* Fixed-height rows where a fallback font (CJK, Indic) has taller metrics than
  Manrope.

Policy: prefer content-sized or flex layouts; where a width is unavoidable,
measure the translated string and ellipsize through the existing text API
instead of overflowing. The pseudo-locale is the detector: IPC screenshots in
`qps` for every panel, compared against English.

## Phases

**Phase 0: survey (small). Done, see [Phase 0 results](#phase-0-results).**
Classify the ~1,300 literals by sink (UI / protocol / log / id) to get the
real count per area; confirm which standalone apps get `LC_MESSAGES` from
`applyRegion` (Files, Images, PDF, Editor, share picker); check whether the
IPC widget tree exposes text extents, which would allow an automated
overflow assertion; check IME in shell text fields; check dead keys and
compose in every text field (see
[First languages](#first-languages-spanish-and-portuguese)); check how
`applications.zig` picks its `Name[xx]` locale and make it use the same
resolver.

**Phase 1: module and tooling.**
`i18n` with `tr`/`trc`/`trn`/`fmt`, plural rules, language resolution, the PO
compiler, `i18n-extract`/`-check`/`-lint`, the `qps` generator. Unit tests for
plural rules, placeholder substitution, fallback chain and catalog lookup.
Convert one small surface end to end as the proof (the power menu: 7 labels
plus the `"Uptime {d}h {d}m"` format). Measure binary size and confirm
`tr` adds nothing to the frame profile (`perf stat`, instructions).

**Phase 2: shell chrome.**
Power menu, taskbar, start menu, calendar and battery popups, notification
toast/OSD text we own, delete/rename dialogs, screenshot selector, tray
chrome, lock screen, polkit dialog. First `qps` layout pass. Lock screen and
polkit dialog are security-sensitive: the strings only change language, never
which action a button performs; keep buttons identifiable by position and
role, not wording.

**Phase 3: Control Center.**
The largest area (609 literals). Most formatted strings live here
(`"Account details · {s}"`, `"Boot time: {s}"`, `"Delete {s}?"`) and need
`fmt`/`trn`. The Region section's language list should show which locales
RediWM itself is translated into. One section per commit; extend the lint list
after each.

**Phase 4: app clients.**
Files (361), Images, PDF, Editor, share picker. Resolve language from the
environment in each `*_main.zig`, before the first frame, alongside theme
loading. Files has selection-count strings
(`"{n} selected, {size}"` built with `if (n == 1) "" else "s"`) that become
`trn`. Audit the hand-drawn Cairo layouts.

**Phase 5: login.**
`rediwm --greeter` and `rediwm-dm`. The greeter writes nothing under `$HOME`
and has no user config, so it takes the system locale (`/etc/locale.conf` via
the DM's environment) or a per-user choice only if the DM already knows it;
this is a decision, see below. `rediwm-dm` and the accounts helper run as root
and must not parse catalogs or build user-facing text: they return error codes
and the unprivileged UI maps them to strings. Audit both for English text
that crosses the boundary.

**Phase 6: docs (last phase of the groundwork).**
Document how to add a language in the wiki (`docs/wiki`), `README.md` and
`TESTING.md`: copy `po/rediwm.pot` to `po/<lang>.po`, translate, run
`zig build i18n-check`, build.

**Later, not part of this plan: adding actual languages.**
Each one is a `.po` file plus a check of fonts and fallback metrics on real
text. A language whose plural rules are not yet in the table needs one
function and a test.

## Phase 0 results

Done 2026-10-08. Read-only; nothing in `src/` changed.

**How many strings.** A script over non-test `src/**/*.zig` (skipping `test`
blocks, comments, log/error/compare lines) classified distinct capitalised or
multi-word literals by whether they feed a UI sink. It misses lower-case
labels and multi-line `\\` literals, so treat the figures as +/-20%.

* In UI-facing areas: 404 distinct strings reach a UI sink, and 814 more are
  unclassified. A 25-string sample of the remainder was ~80% UI text (the rest
  were D-Bus members, config templates, log text). Expect **about 1,000
  translatable strings** (range 800–1,200), not the 1,300 occurrences first
  counted.
* Sink-matched + remainder by area: `control_center` 241+318, `files` 84+134,
  top-level `src/*.zig` 20+155, `network` 22+65, `images` 12+46, `editor`
  13+25, `screenshot` 10+26, `pdf` 3+33, `desktop` 1+33, `polkit` 2+31,
  `start_menu` 7+13, `share_picker` 4+10, `taskbar` 2+4, `notifications` 0+5,
  `ui` 1+6.
* Not translated (protocol, CLI, config template or logs): `ipc` (~290),
  `msg`, `config`, `dbus`, `dm`, `accounts_helper`, `input`, `audio`,
  `capture`, `night_light`, `config_runtime`. Exception: `session` holds a few
  user-facing power/logind errors ("Blocked by an active inhibitor lock.",
  "Lost contact with login service. Try again."), converted by hand in Phase 2.
* Keybinding descriptions ("Increase system volume.", "Move the relevant split
  divider left.") are user-visible and numerous; they count toward
  `control_center`.

**Language reaches launched apps, but not the apps' own code.**
`child_env.apply` calls `applyRegion` (`child_env.zig:34`) and every launch
path goes through `applyChildEnv*`, so apps get `LANG`/`LC_MESSAGES`/`LC_CTYPE`
from `[region] language`, and `LC_ALL`/`LANGUAGE` are removed. The standalone
clients (`files_main`, `images_main`, `pdf_main`, `editor_main`,
`share_picker_main`) read no language variable today; Phase 4 adds the
resolver there, reading `LC_ALL` → `LC_MESSAGES` → `LANG`.

**The compositor does not follow `[region] language` yet.** `applyRegion`
edits only child environments; the compositor's own process environment is
unchanged. `start_menu/applications.zig` builds its `Locale` from that process
environment at startup (`Locale.fromEnv`, and the cache key in
`catalog_cache.envKeys` uses the same variables), so `Name[xx]` desktop-entry
names follow the login locale, not the setting, and do not update when it
changes. The shared resolver replaces both: the cache key must include the
resolved language, and a language change must rescan.

**IPC widget tree.** `WidgetNodeData` carries `label`, `box`, `global_box`,
`clipped` and `text_length`, but not the measured text width, so a test cannot
assert overflow. Phase 1 adds a `text_width` field (layout pixels); the `qps`
tests then assert `text_width <= box.w` for every labelled widget.

**IME in the shell.** None. `input/text_input.zig` relays text-input-v3 and
input-method-v2 for client apps only. The shell's own fields (control center,
start menu, lock, polkit) and the Files/Images/PDF fields take xkb keysyms
only. Irrelevant for Spanish and Portuguese; it confirms CJK input would be a
separate project.

**Dead keys: confirmed broken everywhere but the Editor.**

* Checked with libxkbcommon: on `latam`, `es`, `br`, `pt` and `us(intl)`
  the dead keys (acute, grave, tilde) return **0 bytes** from
  `xkb_state_key_get_utf8`.
* Every text path outside the Editor uses that call with no
  `xkb_compose_state`: `Keyboard.zig:819,847,885` (compositor shell: start
  menu, control center fields, lock screen, polkit, wifi popup, desktop),
  `files/main.zig:547,554`, `images/main.zig:476,483`, `pdf/main.zig:404,411`.
  By code reading, an empty result is dropped (`utf8.len > 0` else no
  character). I have not typed it on a live session.
* Beyond names and search: the **lock screen and polkit password fields**
  read the same way, so a password containing an accent typed with a dead key
  cannot be entered. The same applies to the greeter, which is the same
  compositor. That is a lockout risk for exactly the target users.
* The compose table depends on locale, and not only for tidiness:
  `´`+`c` composes to `ć` in `C`, `en_US` and `es_MX` but to `ç` in
  `pt_BR`. A table loaded from the wrong locale gives Brazilian users the wrong
  letter. `C`/`C.UTF-8` do resolve to a working table (á, ã); an invalid or
  uninstalled locale returns no table and logs an xkbcommon error, so the
  loader needs a fallback to `C.UTF-8`.
* Fix: move `editor/compose.zig` to `ui/compose.zig`; one compose state per
  keyboard in the compositor (reset on focus or layout change) and one per
  client; build the table from the resolved UI language. Composed text for
  lock and polkit goes through the existing `clearKeyScratch` scrub, and a
  pending dead key is cleared when a secret field loses focus. This is a
  separate small change that does not wait for the `i18n` module.
* **Fixed 2026-10-08 (uncommitted).** `ui/compose.zig` replaces
  `editor/compose.zig`: lazy shared table built from the user's language
  (`[region] language` in the compositor, `LC_ALL`/`LC_CTYPE`/`LANG` in app
  clients), locale names normalised to `ll_CC.UTF-8` (a bare `pt_BR` maps to
  the unparseable ISO 8859-1 file), fallback to `C.UTF-8`. Wired into
  `Keyboard.composeShell` (start menu, control center, lock, polkit, wifi
  popup, desktop), Files, Images, PDF (table preloaded before its sandbox) and
  the Editor. A dead key, or the key completing a sequence, never repeats.
  `tests/dead_keys.py` types through a virtual `latam` keyboard under `pt_BR`
  and `es_MX`. Known limits: a key that does not fit a pending sequence is
  swallowed (as in the Editor); a dead key left pending across a lock/unlock
  cycle can combine with the first key of the next lock prompt; text-input-v3
  clients are unaffected (they compose themselves).

## Testing

* Unit tests (`zig build test`): plural rules for every family, placeholder
  substitution and mismatch rejection, fallback chain, PO parser, catalog
  round trip.
* Existing integration tests run unchanged in English. They are the proof
  that the default path is untouched.
* One new integration test per phase launches with `[region] language` set to
  the `qps` locale (with a scratch `XDG_STATE_HOME`, or the run clobbers the
  live autosave layout), opens each converted panel, and checks
  that widgets are still found by `name`, that bounds do not overflow, and
  that IPC screenshots differ from English only in text.
* Per `AGENTS.md`: build Debug and ReleaseSafe, and `strings` the ReleaseSafe
  binary to confirm no test hook leaked.

## Risks

* **The mechanical conversion hides non-text strings.** Wrapping an ID or an
  IPC name in `tr` breaks behaviour only when a translation exists, so it
  would pass English tests. Mitigation: Phase 0 classification by sink, and
  `i18n-check` rejecting `tr` on strings used as map keys or `std.mem.eql`
  operands in the same function where it can see them.
* **Cached rasters keyed by text** stay correct (the key includes the text),
  but anything caching measured widths across a language change must be
  invalidated with the rest on reload.
* **Translations drift** as English changes. `i18n-check` reports stale and
  missing entries; fuzzy-matching is left to the translation tools.
* **Scope creep into RTL and IME**, which are each a project of their own.

## Decisions

Made 2026-10-08, taking the recommendations:

1. **UI language is `[region] language`.** One "Language" setting; no
   separate `ui_language` key.
2. **English text is the msgid**, with `trc` for the few collisions. No
   symbolic keys.
3. **Greeter uses the system locale only** for v1; no per-user choice at
   login.
4. **Translations are `.po` files contributed by pull request.** No hosted
   translation tool.
5. **Right-to-left is out of scope** and needs its own plan (bidi
   reordering plus mirrored layouts).

## First languages: Spanish and Portuguese

The intended first additions (Latin America is the target audience), added
after this plan. Neither needs RTL, an input method or special fonts: Manrope
covers the accents. What they do need from the groundwork:

* **Regional chains.** Locales arrive as `es_MX`, `es_AR`, `es_CO`, `pt_BR`,
  `pt_PT`. Resolution tries the exact tag, then the language, so ship one
  neutral `es` (imperative forms, no voseo or regional vocabulary, serves all
  of Latin America and Spain) and `pt_BR` (`pt` resolves to it unless a
  `pt_PT` catalog exists). Regional overrides are small `.po` files that
  carry only the strings that differ.
* **Plural rules.** Spanish: `n == 1` is singular. Brazilian Portuguese
  differs: 0 and 1 are both singular ("0 arquivo"), European Portuguese
  follows Spanish. CLDR also defines a `many` form for exact multiples of a
  million ("1 millón de archivos"); the table ignores it and uses `other`,
  which is wrong only for counts that large.
* **Length.** Both run roughly 15–30% longer than English, so the `qps`
  pseudo-locale (+40%) is a sufficient stress test.
* **Dead keys and compose (prerequisite, not i18n).** Confirmed broken
  outside the Editor and fixed 2026-10-08; details in
  [Phase 0 results](#phase-0-results).
* **Other dependencies.** `region.formats` already handles LATAM date and
  number differences (comma decimals, 24-hour clock). Desktop entries use the
  same resolver as the UI, so `Name[es]`/`Name[pt_BR]` fall in line.
